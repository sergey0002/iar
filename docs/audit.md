## Концепция продукта (уточнение владельца)

IAR — **портативный инструмент**: папка кладётся в корень любого сайта, URL изображений пропускаются через неё, оптимизированные варианты сохраняются в кеш. Ключевые принципы:

1. **Drop-in портабельность** — никаких внешних сервисов, фреймворков и усложнения развёртывания; работает в любой папке сайта.
2. **Кеш полностью удаляемый** — его можно грохнуть целиком; варианты пересоздаются при первом обращении по URL. *Проверено динамически: полное удаление `cache/*` → первый запрос возвращает 200 и корректно пересоздаёт файл.*
3. **Лог — только для отладки, по умолчанию выключен. Ротация не нужна.**

Аудит ниже учитывает эту концепцию: требования к «enterprise-обвязке» (ротация логов, LRU-квоты кеша, DI-контейнеры) **не являются обязательными** и даны лишь как опции. Замечания, противоречащие концепции текущим кодом (например, `logging => true` по умолчанию), отмечены явно. Архитектурные рекомендации сохраняют портабельность: всё остаётся внутри одной папки, без фреймворков.

## 1. Архитектура и SOLID — 3/10

> Концепция портабельности не требует фреймворков и контейнеров. Рекомендации ниже — про наведение порядка внутри одной папки: несколько классов в `src/` вместо god-script, инъекция через конструктор без DI-контейнера. Это сохраняет drop-in развёртывание.

### A-01 · 🟠 Средний · SRP: `index.php` — god-script
**Где:** `index.php` целиком (секции 1–11 + `serveFile()`).

Один процедурный файл совмещает **10+ ответственностей**: парсинг и валидацию ввода, разрешение путей и security-проверки, content negotiation, построение кеш-ключа, управление кешем (очистка), оркестрацию обработки, HTTP-ответ (заголовки, ETag, 304, редиректы), логирование, потоковую отдачу файла. Функция `serveFile()` (стр. 273) сама по себе смешивает логирование + HTTP-заголовки + редирект/стриминг.

**Следствие:** любое изменение требует правки одного огромного файла; код нетестируем по частям; баги вроде `$reason` (B-01) неизбежны.

**Рекомендация (портабельная):** вынести в `src/` несколько классов без внешних зависимостей: `Request` (парсинг/валидация), `Response` (заголовки/отдача), `CacheStore` (ключи, запись, очистка), `DebugLogger`. Entry point — тонкий контроллер ~30 строк. Никаких фреймворков — всё в той же папке.

### A-02 · 🟠 Средний · OCP: расширение требует правки 3–4 мест
**Где:** `index.php` (whitelist `fm` стр. 106–112, auto_format стр. 141–158, mimes в `serveFile` стр. 275–283), `ResizeService::saveEncoded()` (switch стр. 152–200), `applyResizePolicy()` (switch стр. 127–145).

Добавление формата или режима требует синхронной правки **четырёх** разнесённых switch/массивов. Баг B-04 (`fm=svg`) — прямое следствие: whitelist форматов размазан и не согласован с энкодерами.

**Рекомендация:** единый реестр форматов (mime, энкодер, поддержка анимации, допустимость как `fm`) и стратегии режимов. Новое поведение — новый класс, без правки существующих. Остаётся внутри `src/`.

### A-03 · 🟠 Средний · DIP: жёсткие конкретные зависимости
**Где:** `index.php:227` (`new ResizeService($config)`), `ResizeService.php:24` (`new ImageManager(new Driver())` в конструкторе).

Сервис сам создаёт GD-драйвер внутри себя; подменить драйвер или замокать обработку в тестах невозможно без правки кода.

**Рекомендация (без контейнера):** интерфейсы `ResizerInterface`, `CacheStoreInterface`; инъекция через конструктор; создание объектов — в entry point. Драйвер Intervention — параметр конфигурации. DI-контейнер не нужен — портабельность сохраняется.

### A-04 · 🟡 Низкий · ISP/LSP: интерфейсов нет, «толстый» конфиг-массив
**Где:** `ResizeService.php:18,21` (`private array $config`, `__construct(array $config)`).

Наследования нет — LSP формально не нарушен, но и абстракций нет. Сервис получает **весь** конфиг (пути, логирование, режимы кеша), хотя использует лишь качество/лимиты/дефолты. Опечатка в ключе обнаружится только в runtime (S-03, C-01).

**Рекомендация:** типизированный `Config` DTO с валидацией при загрузке; передавать сервису только нужную секцию.

### A-05 · ⚪ Инфо · Целевая структура (в рамках одной папки, без фреймворков)
```
iar/
  index.php                 # ~30 строк: wiring
  config.php
  src/
    Config.php              # DTO + валидация
    Http/Request.php        # параметры, типы, whitelist
    Http/Response.php       # заголовки, ETag, 304, редирект, stream
    ResizeService.php       # только обработка изображения
    FormatRegistry.php      # форматы, энкодеры, анимация
    CacheStore.php          # ключи, атомарная запись, lock, очистка
    DebugLogger.php         # только отладка, по умолчанию выключен
```

## 2. ООП и качество кода — 4/10

### O-01 · 🟠 Средний · Процедурный entry point, один класс на проект
364 строки процедурного кода в `index.php` против единственного класса `ResizeService`. Кеш-ключи, выбор формата, HTTP — всё в глобальной области. См. A-01.

### O-02 · 🟠 Средний · Отсутствует типизация
**Где:** `ResizeService.php:60,111,152` — `$image` без типа (должен быть `ImageInterface`); `array $config`, `array $params` — неструктурированные массивы вместо DTO (`CropParam`, `ResizeParams`). IDE/статанализ не ловят ошибок; PHPStan поймал бы `$reason` и `$compression` мгновенно.

**Рекомендация:** `declare(strict_types=1)`, типизированные параметры/возвраты, `ImageInterface $image`, DTO для параметров и конфига.

### O-03 · 🟡 Низкий · Нет `declare(strict_types=1)`
Coercive-режим: `(int)$_GET['w']` молча превращает `'abc'` в `0`, массив в `1` (подтверждено, B-11). Строгий режим + явная валидация ввода сделали бы поведение предсказуемым.

### O-04 · 🟡 Низкий · Магические числа в коде
`10000` (потолок кропа, `index.php:125`), `0.1` (clamp 10%, `ResizeService.php:100–101`), `10` (длина хеша, `index.php:167`), `31536000` (max-age, `index.php:305`), `0755`. Часть — в конфиг, часть — в именованные константы.

### O-05 · 🟡 Низкий · Мёртвый и legacy-код
- `$compression` вычисляется и не используется (`ResizeService.php:159`) → B-06.
- `$reason` используется без объявления (`index.php:258`) → B-01.
- Наследие `thubms`: комментарий `index.php:239`, дефолт `SCRIPT_NAME '/thubms/index.php'` (стр. 240), шапка `.gitignore`.
- `.htaccess` защищает несуществующие `download_composer.php` / `resize_class.php`.
- Комментарии «Fixes applied (audit 2026-03-05)» заявляют исправления, которые частично не работают (IMP-12 обещает лимит кропа, но отрицательные значения не ограничены — B-05).

### O-06 · 🟡 Низкий · Стиль: PSR-12 не соблюдается
`index.php` — табы, `ResizeService.php` — 4 пробела; `use App\ResizeService;` после `require` (стр. 21); смешение стилей скобок. Нет `.editorconfig`, нет форматтера. **Fix:** PHP-CS-Fixer (PSR-12) + `.editorconfig`.

### O-07 · 🟡 Низкий · Непоследовательный доступ к конфигу
Большинство ключей через `?? default`, но `$config['cache_invalidation']` (`index.php:182`) и `allowed_extensions` — напрямую. При отсутствии ключа — warning → сломанные заголовки (E-01). Единый DTO (A-04) снимает проблему.

## 3. Производительность — 5/10

**Замеры стенда** (PHP 8.3 WASM, относительные величины; изображение 1200×800):

| Сценарий | Среднее время |
|---|---|
| Cache HIT, `logging=true` | **1.43 мс** |
| Cache HIT, `logging=false` | **1.07 мс** |
| Накладные расходы логирования на горячем пути | **+34%** |
| Cache MISS (генерация 150px) | **~32 мс** (×22 к hit) |

### P-01 · 🟠 Средний · Отладочный лог включён по умолчанию и тормозит горячий путь
**Где:** `config.php:45` (`logging => true`), `serveFile()` стр. 317–349.

По концепции лог — только для отладки и **по умолчанию выключен**, но в конфиге он включён. Каждый cache-hit выполняется `file_put_contents(..., LOCK_EX)` — дисковый I/O + блокировка. Замер: **+34%** латентности hit; под нагрузкой `LOCK_EX` сериализует воркеры. **Подтверждено:** 31 hit → 31 строка лога.

**Рекомендация:** `logging => false` по умолчанию (приведение к концепции). Ротация не нужна — лог отладочный и выключен. При включении для отладки overhead допустим.

### P-02 · 🟠 Средний · Cache stampede + неатомарная запись
**Где:** вендор `File::save()` → `@file_put_contents` прямо в финальный путь; `index.php:210–224`.

N параллельных запросов uncached-изображения → N генераций (×32 мс) + читатели могут отдать недописанный файл. `mkdir` без `@` и повторной проверки — гонка → warning → сломанные заголовки.

**Рекомендация:** временный файл + атомарный `rename`; `flock` на время генерации; `@mkdir` + recheck. См. B-10.

### P-03 · 🟠 Средний · Запрос без операций перекодирует оригинал
**Подтверждено:** `photo.jpg` без параметров → 57 397 → 36 271 B, полное декодирование + JPEG q82. Трата CPU и потеря качества там, где изменений не просили.

**Рекомендация:** если `w=h=0`, кропа нет, формат не меняется — `copy()` в кеш или редирект на оригинал. См. B-14.

### P-04 · 🟡 Низкий · `glob()`-скан кеша на каждом промахе
**Где:** `index.php:218–224` (`cache_auto_clean`). Каждый miss сканирует каталог кеша; каталог растёт → стоимость растёт. По концепции кеш можно грохнуть целиком, поэтому агрессивный GC не обязателен — но спецсимволы glob ломают очистку (B-09), а скан на горячем пути лишний.

**Рекомендация:** очистку старых версий делать точечно (по префиксу ключа) либо вынести из горячего пути; полный сброс кеша — штатная операция по концепции.

### P-05 · 🟠 Средний · Отдача через PHP по умолчанию держит воркер
**Где:** `config.php:31` (`redirect_to_cache => false`), `serveFile()` → `readfile`.

Медленный клиент занимает PHP-воркер на всё время передачи. Режим редиректа на статику реализован, но выключен и сломан для кастомного `cache_dir` (B-08). README заявляет дефолт `true`.

**Рекомендация:** после исправления B-08/B-02 сделать `redirect_to_cache=true` дефолтом; для nginx — `X-Accel-Redirect`.

### P-06 · 🟡 Низкий · Повторные stat-вызовы
`serveFile()` вызывает `filemtime`/`filesize` 3–4 раза (ETag стр. 287, Content-Length стр. 298, лог стр. 331–332). Stat-кеш смягчает, но чище один `stat()` и переиспользование.

### P-07 · 🔴 Высокий · Полное декодирование входа в память
См. S-02: 140 Мп → OOM. И безопасность, и производительность (48 Мп ≈ 200 МБ на воркер). Лимит мегапикселей до `read()` обязателен.

### P-08 · ⚪ Инфо · Что уже хорошо
ETag без чтения файла, `scaleDown` не увеличивает маленькие изображения, режим редиректа и `static_mode` задуманы верно, кеш-ключ учитывает mtime. **Кеш полностью удаляемый и пересоздаётся по первому URL — проверено, соответствует концепции.**

## 4. Безопасность — 4/10

### S-01 · 🔴 Высокий · Хранимый XSS через SVG (PHP-путь без CSP)
**Где:** `serveFile()` стр. 273–363; `.htaccess` стр. 26–33; `processSvg()`.

CSP для `.svg` ставится только при отдаче Apache напрямую. В дефолте (`redirect_to_cache=false`) SVG идёт через PHP **без CSP и nosniff**. **Подтверждено:** SVG с `<script>alert(document.domain)</script>` → `200 image/svg+xml`, скрипт в теле. Если сайт принимает SVG-загрузки — выполнение JS в домене сайта.

**Fix:** в `serveFile()` для svg всегда `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, `X-Content-Type-Options: nosniff`; санитизация SVG или принудительная растеризация.

### S-02 · 🔴 Высокий · DoS: входные мегапиксели (память)
**Подтверждено:** JPEG 14000×10000 (файл 2.2 МБ) → `Fatal: Allowed memory size exhausted`, 500 с путями. `max_width/height` лимитируют только выход.

**Fix:** `getimagesize()` до `read()`, лимит мегапикселей (например ≤40 Мп) и размера файла в конфиге.

*Про рост кеша:* по концепции кеш полностью удаляемый, поэтому обязательные LRU-квоты не требуются — достаточно документировать штатный полный сброс. Остаточный риск исчерпания диска при отсутствии обслуживания остаётся (миллиарды комбинаций параметров без аутентификации); опционально — квота/rate-limit на генерацию средствами веб-сервера. Это не блокер концепции, но стоит упомянуть в README.

### S-03 · 🟠 Средний · Fail-open при ошибочном `images_base_dir`
**Где:** `index.php:41`. `realpath()===false` не обрабатывается → `$baseDir='/'` → доступ к любым картинкам ФС. **Подтверждено:** при несуществующем base_dir запрос `?name=www/photo.jpg` отдаёт файл от корня.

**Fix:** явный 500 при `realpath()===false`.

### S-04 · 🟠 Средний · `display_errors=1` → утечка путей и слом ответов
**Где:** `index.php:2–4`. **Подтверждено:** варнинги/фаталы выводят полные пути; любой вывод до `header()` ломает заголовки (B-01, B-11). **Fix:** `display_errors=0`, `log_errors=1`, единый обработчик (E-01).

### S-05 · 🟠 Средний · `.htaccess`: открытые служебные файлы, листинг, мёртвые правила
Не закрыты `log/`, `composer.*`, `vendor/`, `config.php`, dotfiles; нет `Options -Indexes`; `FilesMatch` защищает несуществующие legacy-файлы; `Order/Deny` — синтаксис Apache 2.2. При деплое через `git clone` (рекомендация README) наружу доступен `.git/`. См. DEP-01/DEP-03.

### S-06 · 🟠 Средний · Перезапись `name` через QSA
**Подтверждено:** `/iar/photo.jpg?name=small.png` отдаёт `small.png` — пользовательский параметр перекрывает путь из URL. Валидация не обходится, но семантика URL/логов ломается. **Fix:** брать путь из `REQUEST_URI`, не из `$_GET['name']`.

**Позитив (проверено):** path traversal закрыт корректно — `../`, URL-кодированные обходы, симлинки наружу → 404/403 (6 сценариев); whitelist расширений/режимов/гравитации работает; clamp `w/h` подтверждён (99999 → 2000).

## 5. Логика и корректность — 5/10

### B-01 · 🔴 Высокий · Сломан fallback: `$reason` не определена
`index.php:258`. При ошибке обработки: `Warning: Undefined variable $reason` → вывод → `headers already sent` → **302 на оригинал не отправляется**. **Подтверждено:** `corrupt.jpg`, SVG без Imagick → `200 text/html` с варнингами. **Fix:** задать причину, убрать display_errors, логировать до заголовков.

### B-02 · 🔴 Высокий · `immutable` на год противоречит mtime-инвалидации
`index.php:305`. **Подтверждено:** после смены оригинала серверный кеш обновляется, но браузер с `immutable` не перепроверяет → старая картинка до года. В режиме редиректа кешируется сам 302 → после `auto_clean` редирект ведёт на удалённый файл → **404**. **Fix:** `no-cache`/короткий max-age для mtime-режима; `immutable` только для static/версионированных URL; не слать immutable на редиректы.

### B-03 · 🟠 Средний · Коллизия кеш-ключа — отдаётся чужое изображение
`index.php:165`: `str_replace(baseDir,'',path)` вырезает **все** вхождения. `/www/www/photo.jpg` → `photo.jpg` → тот же хеш, что у `/www/photo.jpg`. **Подтверждено:** два разных изображения с одним mtime → один кеш-файл, вложенный запрос вернул кеш базового. **Fix:** `substr($filePath, strlen($baseDir))`; полный md5 вместо 10 символов.

### B-04 · 🟠 Средний · `fm=svg` для растра → JPEG в `.svg`
Whitelist `fm` = `allowed_extensions` (включая svg); `saveEncoded()` default → `toJpeg`. **Подтверждено:** `.svg`-файл с магией JPEG и MIME `image/svg+xml`. **Fix:** отдельный whitelist выходов `jpg/jpeg/png/webp/avif/gif`; явное исключение вместо default.

### B-05 · 🟠 Средний · Кроп: negative, >100%, clamp без коррекции offset
`index.php:125` (нет нижней границы), `ResizeService.php:100–101`. **Подтверждено:** `ct=-50` → белая полоса; `ct=95p` → 40 чёрных строк; `ct=150p` → полностью чёрное изображение. **Fix:** clamp значения в `[0, размер]`/`[0,100%]`, пересчёт offset после clamp.

### B-06 · 🟠 Средний · `png_compression` — мёртвая опция
`ResizeService.php:159` — переменная не передаётся; вендор `imagepng(..., -1)` жёстко. **Подтверждено:** при 0 и 9 файлы побайтово идентичны. **Fix:** удалить опцию из конфига/README или реализовать свой энкодер/Imagick.

### B-07 · 🟠 Средний · Авто-WebP убивает анимацию GIF
**Подтверждено:** 2 кадра → 1 при `fm=webp` и авто-WebP. При `auto_format=true` любой современный браузер получает статику. GIF→GIF анимацию сохраняет. **Fix:** детект анимации и пропуск авто-конвертации для анимированных GIF.

### B-08 · 🟠 Средний · Редирект игнорирует кастомный `cache_dir`

### B-09 · 🟠 Средний · `auto_clean`: glob-спецсимволы и неполнота

По концепции кеш можно грохнуть целиком — но это ручная операция, а заявленная *автоматическая* инвалидация при обновлении оригинала работает неполно: браузер/CDN могут получить устаревший вариант другого размера. **Fix:** экранирование имени/скан каталога; паттерн всех размеров `имя__*__hash_*`.

## 6. Логирование — 4/10

> Концепция: лог — **только для отладки, по умолчанию выключен, ротация не нужна**. Оценка ниже — о соответствии кода этой концепции и о безопасности отладочного лога, а не о требованиях к production-логированию.

### L-01 · 🟠 Средний · Лог включён по умолчанию вопреки концепции
**Где:** `config.php:45` — `'logging' => true`.

По концепции дефолт должен быть `false`. Сейчас каждый запрос (включая cache-hit) пишется в лог: **подтверждено** 31 hit → 31 строка, +34% латентности (P-01). Отладочный лог без ротации при включённом дефолте растёт неограниченно — но по концепции ротация и не нужна, потому что лог должен быть выключен.

**Рекомендация:** `logging => false` по умолчанию. Ротацию не внедрять (соответствует концепции). В README явно: «лог только для отладки, включается вручную».

### L-02 · 🟠 Средний · Логи публично доступны и закоммичены
Каталог `log/` в webroot, `.htaccess` его не закрывает (S-05) → при включённой отладке логи скачиваются напрямую. `log/2026-03-05.log` отслеживается git (внутренние URL/пути). **Fix:** `Require all denied` для `log/` (или вынести из webroot), `git rm --cached log/2026-03-05.log`.

### L-03 · 🟡 Низкий · Отладочному логу не хватает структуры (опционально)
Plain-text без уровней, request-id, длительности, статуса. Для отладки полезно видеть `duration_ms`, hit/miss, причину ошибки. Это улучшение удобства отладки, не обязательное требование. **Fix (опция):** единый формат с уровнями и длительностью; счётчики hit/miss.

### L-04 · 🟡 Низкий · Чувствительные данные в отладочном логе
Полный `REQUEST_URI` + все GET-параметры + пути файлов (возможные PII, токены в query). При включённой отладке на боевом сайте — риск утечки. **Fix:** минимизация полей, редактирование чувствительных параметров; напоминание в README, что лог только для отладки.

### L-05 · 🟡 Низкий · `@`-подавление и два несвязанных канала
`@file_put_contents` — потеря логов молча. `error_log()` в `ResizeService` пишет в PHP-error-log, запросы — в свой файл: единой картины нет. **Fix:** один канал отладки, проверка результата записи.

### L-06 · 🔴 Высокий · FAIL-ветка логирует несуществующую `$reason`
См. B-01 — логирование ошибки само генерирует ошибку и ломает ответ.

### L-07 · 🟡 Низкий · Теоретическая log-injection
В FAIL-ветке поле `REDIRECT` содержит декодированное имя файла — при имени с `\n` возможна подделка строк лога. `PARAMS` защищён `json_encode`, `URL` — сырой REQUEST_URI. Риск низкий. **Fix:** экранирование переводов строк во всех полях.

## 16. Приложение: методика и стенд

- **Стенд:** PHP 8.3.0 (WASM; GD: JPEG/PNG/WebP/GIF; без AVIF/Imagick/exif), `memory_limit=256M`; исходники `intervention/image` 3.11.7 и `intervention/gif` 4.2.4 точно по lock + PSR-4 автозагрузчик.
- **Данные:** градиент 1200×800, PNG с альфой 100×100 и 400×300, анимированный GIF (2 кадра), JPEG с EXIF Orientation=6, битый `.jpg`, SVG со скриптом, имена с пробелом/кириллицей/`&`/`[ ]`, JPEG 48 Мп и 140 Мп.
- **Сценарии:** ~60 запросов (безопасность, параметры, форматы, кроп, кеш, редиректы, заголовки, DoS, имена) + микробенчмарк hit/miss/logging + **тест полного сброса кеша**.
- **Ограничения:** Apache/mod_rewrite не эмулировался (`.htaccess` — статически); ветки AVIF/Imagick — статически. Выводы «подтверждено» воспроизведены динамически.
- **Исходный репозиторий не изменялся**; все эксперименты — в изолированной копии.
